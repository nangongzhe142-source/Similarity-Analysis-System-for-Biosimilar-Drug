## 2. D18 — 主数据源查清与生成器修复

### 2.2 实测验证过程

## 3. D17 与 D21 — 数据集处置

### 3.1 D17 取代 D3

用户选择「4 项无规则项目完全不跑分析」，与先前 D3「P13/P14 只算不判」相反。已按新决策处理，并在计划中显式标注取代关系，避免两条决策并存。

后果：PXD023358 的 625 MB 二硫键 RAW 失去唯一消费方。

### 3.2 保留取舍

按用户选择，只删 RAW，保留 8.8 MB 小文件：

- **保留理由**：`NISTmAb.fasta` 是 P1 定为权威的 NISTmAb 序列（HC 450 aa / LC 213 aa），与二硫键无关，是 MS1/MS-MS 序列覆盖分析的理论序列来源，也是暴露 PXD063988 中 449 aa 缺陷 FASTA 的那把尺子。
- 36 个二硫键鉴定表共 8.8 MB 一并保留，供 D17 将来被重新审视时使用，但**在 D17 有效期间不得接入任何 adapter**，已写入 manifest。

### 3.3 D21 — 更小更强的 RAW 验证样本

删掉唯一 RAW 会使 D12 要求的「RAW 实机转换成功」失去样本。查 PXD023358 全部 36 个 `.raw`，**最小 425.2 MB**，同数据集内无廉价替代。

改用 ProteoWizard 仓库中 Thermo 读取器自带的回归测试数据：

| 文件 | 体积 | SHA-256 前 16 位 | magic bytes |
|---|---|---|---|
| BSA-FT-HCD.raw | 342.9 KB | `45dbaea253856f3f` | `01a1460069006e00` |
| BSA-FT-ETD.raw | 340.4 KB | `d63a86285709d161` | `01a1460069006e00` |
| FT-HCD-MSX.raw | 76.5 KB | `b3d97b3856dd1e8d` | `01a1460069006e00` |
| IT-HCD-SPS.raw | 279.1 KB | `c18f8d01e3400702` | `01a1460069006e00` |

四者 magic bytes 与被删除的 625 MB 生产 RAW 前 8 字节**完全一致**，因此走的是同一条类型校验路径。合计 **1.04 MB 替代 625 MB**，压缩 1/600。

它们是厂商读取器自己的回归基准：**读不了就说明 msconvert 本身坏了**，而不是样本古怪，作为 P6 的验证样本比任意生产 RAW 更强。`BSA-FT-HCD.raw` 还与站点既有 BSA 演示（`verify:demo` 复现 66398.19 Da）对齐，使转换产物有已知蛋白背景。

### 3.4 账目诚实性

`fixtures.lock.json` 中该 RAW 的条目**未删除**，而是移入 `deletedFiles` 并补 `deletedOn` 与 `deletionReason`。它记录的 SHA-256 `41c646e3910471ba…` 是真实下载并全量哈希过的证据，值得保留；同时移出 `files` 后 `--verify` 不会把它误报为缺失。

## 4. D22 — 宿主机原生工具无法处理中文工作区路径

这是本轮最重要的意外发现，影响范围远超 Tesseract。

### 4.1 实测证据

| 调用方式 | 结果 |
|---|---|
| `TESSDATA_PREFIX` = 中文路径 | `Warning: TESSDATA_PREFIX … does not exist, ignore it`；**静默回落**到 Program Files，只列出 eng/osd |
| `tesseract --tessdata-dir` = 中文路径 | **硬崩溃** `terminate called after throwing an instance of 'std::filesystem::__cxx11::filesystem_error'`；错误消息中路径显示为 `ÉúÎïÀàËÆÒ©ÅÐ±ðÏµÍ³`，即 UTF-8 字节被按 ANSI 重新解释 |
| `TESSDATA_PREFIX` = `C:\bsim-tessdata-test`（ASCII） | 正常列出 **chi_sim / eng / osd** |
| Docker bind mount 中文路径 → `/data` | **完全正常**，容器内列出全部 5 个文件并输出 `MOUNT_OK` |

两种失败模式中，**静默回落比崩溃更危险**：程序不会报错，只会「找不到中文」，而原因看起来像模型能力问题而非路径问题。

### 4.2 影响面

不止 Tesseract。D5 的 `Comet.exe`、D12 的 `msconvert` 若在宿主机直调，同样会撞上这个问题。

### 4.3 确立的工程约束

所有原生二进制（tesseract、comet、msconvert）**一律在容器内执行**，宿主中文路径只通过 bind mount 暴露，容器内路径保持 ASCII（`/app/...`）。D7 选定的 Docker 方案恰好使这条约束天然成立，**无需迁移工作区**。

若将来必须在宿主机直调某个原生工具，须先把输入拷贝到 ASCII 临时目录，并在日志中记录该拷贝。

## 4A. 下载器缺陷 — 静默短读被当成下载成功

下载 PXD063988 的两个 mzML 时暴露出下载器的一个真实缺陷，**两个文件都恰好停在 47,761 字节**，同一个数字。

### 4A.1 排除误判

先看 `.part` 的内容，确认它不是错误页：

```xml
<?xml version="1.0" encoding="utf-8"?>
<indexedmzML xmlns="http://psi.hupo.org/ms/mzml" …
```

**是真正的 mzML 前缀**。所以不是 404 页面、不是目录列表，而是真实内容被截断。

### 4A.2 根因

直接探测服务器：

| 项目 | 值 |
|---|---|
| `Content-Length` | **797,649,988** |
| `Accept-Ranges` | `bytes` |
| `Content-Encoding` | 无 |
| `Connection` | `close` |
| 单次 GET 实际读到 | **104,972,288** 字节后静默断流 |

同一个文件，两次尝试分别在 47,761 和 104,972,288 字节处结束 —— **截断点是随机的**，PRIDE 的 HTTPS 端点会掐断长时间传输。

关键在于：连接被掐断时 `response.read()` **返回空字节串而不抛异常**，内层循环因此正常退出，下载器把短读当成了「读完」。原代码的尺寸断言在重试循环**之外**，所以它只能事后报错，永远不会触发续传。

紧接着发的 Range 请求立刻收到 `RemoteDisconnected`，说明服务器还会拒绝过密的重连。

### 4A.3 第一轮修复：把短读定性为失败

`download_one()` 改为：

1. 内层读循环结束后，若 `written < expected_bytes`，抛出新的 `ShortRead(ConnectionError)`，使其落入既有的重试分支并带 `Range` 续传。**短读从此被定性为传输失败，而不是完成。**
2. 重试预算改为「**按停滞**计数」而非按尝试次数计数：有进展的尝试把 `stalled` 归零，无进展才累加。
3. 加绝对上限，防止服务器每次只吐几个字节把循环永久续命。
4. 日志打印每次尝试的实际增量，使停滞与缓慢可区分。

**结果：不够。** 实跑到 **639.7 MB / 669.4 MB（95.6%）** 后连续 4 次零进展而放弃；第二个文件只到 83.7 MB。日志揭示了服务器的真实行为模式：

```text
attempt  3 interrupted (stream ended at 189620224 …); gained 180.8 MB
attempt  4 interrupted (stream ended at 189665280 …); gained  44.0 KB
attempt  5 interrupted (stream ended at 189906944 …); gained 236.0 KB
attempt  6 interrupted (stream ended at 340168704 …); gained 143.3 MB
attempt  7 interrupted (stream ended at 340414464 …); gained 240.0 KB
…
attempt 18 interrupted (Remote end closed connection without response); gained 0.0 B
attempt 19 interrupted (Remote end closed connection without response); gained 0.0 B
attempt 20 interrupted (Remote end closed connection without response); gained 0.0 B
```

即：一个开放式 `Range: bytes=N-` 请求能撑 40–240 MB，随后被掐断；接着服务器进入一段**拒绝重连**期（连 `RemoteDisconnected` 都发生在建连阶段），此时原来 5/10/15 秒的退避太短，撑不到它恢复。

### 4A.4 第二轮修复：有界区间 + 指数退避

关键认识：**对策不是更耐心地重试整个文件尾部，而是不要发出长请求。** 服务器容忍短请求，掐断长请求。

1. 新增 `fetch_window()`，每次只请求 `Range: bytes=N-(N+32MB-1)`。单个请求在当前速率下约 60 秒完成，通常在被掐断前就结束；失败也只损失一个区间而非整条尾部。区间返回字节少于请求量即抛 `ShortRead`。
2. 非 206 响应直接判为失败，不再「服务器忽略 Range 就从零重来」——从零重来会丢掉几百 MB 已验证的字节。
3. 退避改为指数增长并封顶：`min(5 × 2^(stalled−1), 120)` 秒，允许 8 次连续无进展，累计等待约 6.5 分钟，足以熬过限流窗口。
4. 新增越界保护：若磁盘字节数超过声明大小，立即报错而非静默接受。
5. 保留 `stream_whole()` 作为无声明大小时的退路，此时既无法分区间也无法检测截断，只能靠哈希留证。

### 4A.5 验证

第一个文件**完整落地**：

```text
window at 639.7 MB interrupted (Remote end closed …); gained 0.0 B, retrying in 5s
window at 639.7 MB interrupted (Remote end closed …); gained 0.0 B, retrying in 10s
669.4 MB / 669.4 MB (100%) at 333.7 KB/s
ok  sha256=a539c3dbd3b2fb1e8d8a18f4caed36bc…  669.4 MB
```

卡了两轮 55 分钟都过不去的 639.7 MB 位置，在有界区间模式下 15 秒退避后一次通过。

第二个文件也完整落地，指数退避实测生效——在 186.1 MB 与 347.3 MB 处各连续被拒 4 次（5s → 10s → 20s → 40s），均在第 40 秒后恢复：

```text
760.7 MB / 760.7 MB (100%) at 357.5 KB/s
ok  sha256=ba789ac58831adb1c27dd55030125293…  760.7 MB

files: 6   bytes: 1.4 GB   failures: 0
```

两个文件的磁盘字节数与服务器声明的 `Content-Length` **完全相等**（701,961,275 与 797,649,988）。全过程耗时 34 分钟。

### 4A.6 独立校验 — 不能只信自己算的哈希

`download_fixtures.py --verify` 重新哈希磁盘文件并与 `fixtures.lock.json` 比对，全部 `[OK]`。但这只证明「字节自写入以来没变」，**两个数字都来自我们自己**，无法证明这些字节就是投递者产出的字节。对一个需要几十次区间续传拼装起来的 800 MB 文件来说，这个区别是实质性的。

每个 PRIDE 投递自带 `checksum.txt`，内含投递者在自己机器上算的 SHA-1。据此新建 `verify_published_checksums.py`，用**第三方的数字**做见证：

```text
=== PXD023358   checksum.txt lists 74 files  -> sha1   verified 37 files, 0 mismatched
=== PXD054948   checksum.txt lists 48 files  -> sha1   verified 18 files, 0 mismatched
  [OK] 20230421_CM-RG7221-IdeS-DTT_100ng.wiff.scan
       316,821,841 bytes  sha1=22bf695ff4f14996eed8403d0aa7e6673e396ecc
=== PXD063988   checksum.txt lists 150 files -> sha1   verified  5 files, 0 mismatched
  [OK] 20241115_Z1_UM1_shamo002_EXT00_SA_CHYMO_CID_100ng_02.mzML
       797,649,988 bytes  sha1=90ef0e3be8f4811a14cd20fb089575d255dd64bf
  [OK] 20241115_Z1_UM1_shamo002_EXT00_SA_TRYPSIN_EACID_RCE_KE9_100ng_03.mzML
       701,961,275 bytes  sha1=a346078d812bea1c3e892fdf70c1934f1cdf78ca

verified against depositor checksums: 60 OK, 0 mismatched, 0 not listed
```

**60 个文件全部通过，0 不匹配，0 未列出。** 这是「数据完整」这句话目前能拿到的最强证据。

实现上有两个坑：PXD063988 的 `checksum.txt` 是 `<UNC 路径>\t<sha1>` 顺序，摘要在**第二列**，与常见的 `<digest>  <name>` 相反，所以解析器两种顺序都接受；路径含 Windows 盘符与 UNC 前缀，`pathlib` 在 POSIX 语义下不会切分，故显式按 `[\\/]` 取末段。摘要算法由长度推断（32/40/64 → md5/sha1/sha256），不硬编码。

有 mismatch 时脚本返回非零，可用于卡构建。

**这个缺陷的意义**：尺寸断言原本被我当作冗余保险，实际它是唯一发现问题的机制。若当初没写这条断言，仓库里会静静躺着两个看起来正常、实则只有 6% 内容的 mzML，而后续所有基于它们的覆盖率结论都会是错的，且极难追查。

## 4B. 附带发现 — PRIDE API 的文件大小可能过期

下载器每轮都在 `PXD023358/README.txt` 上失败，`.part` 反复停住。查清如下：

| 来源 | 声明大小 |
|---|---|
| PRIDE API `fileSizeBytes` | **4,596** 字节 |
| HTTPS `GET`，`Content-Length` | **19,353** 字节 |
| HTTPS `Range: bytes=0-`，返回 206 | **19,353** 字节 |

内容是稳定的（两种请求方式一致），**过期的是 API 元数据**。下载器第 190 行的尺寸断言因此每次都正确地拒收该文件——这正是断言该有的行为，不应为它放宽。

处置：给 manifest 增加 `excludeFiles`（附逐条理由），`select_files()` 中在所有选择规则**之后**应用，使其能覆盖扩展名规则。README.txt 是 PRIDE 自动生成的投递说明，无分析价值，排除而非弱化校验。

**这条发现的意义超出该文件本身**：PRIDE API 报的大小不能无条件信任。本轮真实数据文件的大小全部吻合，只有 PRIDE 自动生成的 README 过期，所以尺寸断言可以保留；但将来若有真实数据文件在此断言上失败，第一步应先核对服务器实际 `Content-Length`，而不是直接怀疑下载过程。

**两类失败必须区分开**：§4A 的 mzML 是「服务器实际大小与 API 一致，但传输被截断」，正确处置是续传；本节的 README 是「服务器实际大小与 API 不一致，内容本身完整」，正确处置是排除。两者都表现为尺寸断言失败，但修复方向相反 —— 判断依据是实测 `Content-Length` 与 API 声明是否相符。

| eng | 宿主安装拷贝（保证与宿主逐字节一致） | 3.92 MB | 见 manifest |
| osd | 宿主安装拷贝 | 10.07 MB | 见 manifest |
| chi_sim | `tesseract-ocr/tessdata_best` | 12.47 MB | 见 manifest |

合计 26.47 MB。Tesseract 只在 `TESSDATA_PREFIX` 目录内解析语言，所以 `eng` 与 `osd` 必须一并放入，不能只放 `chi_sim`。

变体选 `tessdata_best` 而非 `tessdata_fast`：图谱轴标签是短字符串，**错一位数字就毁掉整条校准**，精度远比吞吐重要。理由已写入 `tessdata.manifest.json`。

## 8. 局限性

1. **chi_sim 尚未做过一次真实 OCR**。目前只证明了 Tesseract 能在 ASCII 路径下**识别到**该语言包，没有证明它能正确读出中文轴标签。真实 OCR 验证属于 P14 范围，届时必须在容器内做，且不得跳过。
2. **pwiz Thermo 样本尚未真实转换过**。它们只被验证为真正的 Thermo RAW（magic bytes 匹配），msconvert 能否读通要等 P6。**在 P6 跑通前，UI 不得声称支持 RAW。**
3. **D22 的约束只在 Tesseract 上取得实测证据**，Comet 与 msconvert 的同类失败是基于同一机制的合理推断，尚未逐一实测。P6 与 P9 应各自记录一次实测结果。
4. **`assert_expected_layout` 只校验表头文本**，不校验行序。若将来 Sheet2 插入或删除数据行，`ROW_CONFIG` 的行号映射会静默错位，而断言不会触发。这是已知缺口，行级校验留待需要时再补。
5. **V2 工作簿仍可能被继续人工编辑**。按 D19（v2_frozen 选项 a）用户已声明冻结 Sheet3，但 Sheet1/Sheet2 现在也成了主数据源，其变动会直接影响生成结果。`verify:schemes` 的 SHA-256 校验能捕获文件改动，这一保护现在覆盖面更重要了。
6. `log/2026-08-14-s14-实机演示.md` 有一处非本次改动（`###` 后多一个空格），按「不动无关文件」的规矩未作修改，在此备案。
