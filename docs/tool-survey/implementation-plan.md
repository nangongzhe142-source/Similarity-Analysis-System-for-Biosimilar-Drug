# 开源工具调研与可行性证明 — 实施计划

> 本文件是「生物类似药药学相似性分析工具调研与部署」任务的唯一进度记录。
> 每完成一步，在文末「进度日志」追加 `Done` 与两行总结，不得跳步、不得回填。

## 一、任务定位（本轮的目标与非目标）

### 目标

**证明可行性，而不是完成真实的相似性分析。**

具体含义：对框架中的每个分析点，用**可复现的证据**回答四个问题：

1. 这条分析路径上，是否存在真实可用的开源工具？
2. 这个工具在本机**真的装得上、跑得动**吗？（不是读文档推测）
3. 它的输出**能不能对接**到框架定义的检测指标与判定原则上？
4. 能否在网站的**检测方法模块**里当场跑通一条最小演示，并让读者核验数据来源与公式？

### 非目标（明确不做）

- 不做真实的生物类似性判定，不产出任何可用于监管申报的结论；
- 不处理真实实验数据（当前无真实数据）；
- 不实现后端服务、文件上传或质谱原始文件在线处理；
- 允许在检测方法模块内嵌**浏览器端实机演示**（合成数据、当场计算），不得呈现为监管结论；
- 不追求工具覆盖率，宁可写「未找到」也不凑数。

### 贯穿全文的免责声明

以下两条必须出现在每一份大类报告的开头，以及每个工具的推荐结论中：

- 「工具能运行」≠「方法学已验证」≠「符合 GxP / 21 CFR Part 11」；
- 「两组数据数值接近」≠「生物类似性成立」。

## 三、能力层级与部署层级定义

### 能力层级（工具在分析链条上的位置）

| 级 | 含义 |
|---|---|
| A | 原始数据读取与格式转换 |
| B | 峰检测、定量或特征提取 |
| C | 数据清洗、批次归一化、对齐 |
| D | 候选药与参照药对比 |
| E | 统计等效性 / quality range / 置信区间计算 |
| F | 图表与报告生成 |
| G | 端到端工作流或平台 |
| H | 仅能作为示意性可行性说明 |

### 部署层级（本任务的核心证据）

| 级 | 含义 | 证据要求 |
|---|---|---|
| L0 | 未部署，仅文档判断 | 必须标注「未验证」 |
| L1 | 安装成功，版本号可打印 | 安装命令 + 版本输出 |
| L2 | 官方示例数据跑通 | 命令 + 输出片段 + 与文档一致性说明 |
| L3 | 合成/公开数据跑通 | 命令 + 输入数据来源 + 输出数值合理性论证 |
| L4 | 与本项目某分析点的目标数据格式跑通 | 输入输出与该检测项目的检测指标对得上 |
| L5 | 输出可被前端消费 | 已转成结构化 JSON，字段与 `models.ts` 可对齐 |
| L6 | 已接入 Next.js 并有自动化测试 | CI 可复现 |

**硬性约束**：实际部署层级低于 L2 的工具，横向比较中「技术可行性」一项不得高于 2 分；
L0/L1 的工具一律不得描述为「可用」「已验证」「可行」。

## 四、一级结构大类的分析点清单

来源：`src/data/characterization-items.ts`，全部 `category: "primary-structure"`，
均为常规项（`isSupplementary: false`）。共 **11 个检测项目 / 33 条方法条目**。

|---|---|---|---|---|---|---|---|

| 2 | `deglycosylated-intact-mass` | 脱糖完整分子质量 | 98 | 酶法脱糖后 LC-ESI-MS | 脱糖完整质量(Da) | 定性/图谱＋理论质量核对 | 无 |
| 3 | `light-chain-mass` | 轻链分子质量 | 185 | 还原/亚基 LC-MS | 轻链质量(Da) | 定性/图谱＋理论质量核对 | 无 |
| 4 | `non-deglycosylated-heavy-chain-mass` | 未脱糖重链分子质量 | 272 | 还原后重链 LC-MS | 重链质量分布(Da) | 定性/图谱＋理论质量核对 | 无 |
| 5 | `deglycosylated-heavy-chain-mass` | 脱糖重链分子质量 | 359 | 脱糖并还原后 LC-MS | 脱糖重链质量(Da) | 定性/图谱＋理论质量核对 | 无 |

| 9 | `n-c-terminal-sequence` | N/C 端序列及末端异质性 | 907 | 肽图 LC-MS/MS；必要时 Edman 降解 | 端基序列、焦谷氨酸化、C 端 Lys 比例 | 定性序列＋定量分布 | 有 |

| 11 | `disulfide-bonds` | 二硫键连接图谱 | 1081 | 非还原肽图 LC-MS/MS | 连接肽、预期连接覆盖、异常连接 | 直接定性比对 | 有 |

### 从清单中读出的三个结构性事实

**事实一：方法高度集中。** 33 条方法条目中，绝大多数落在三种技术上——完整/亚基质谱去卷积（项目 1-5）、
肽图 LC-MS/MS（项目 6-9、11）、化学显色法（项目 10）。这印证了「按大类找共用工具」的判断：
一套质谱工具链若能跑通，即可覆盖本大类 11 个项目中的 10 个。

**事实二：判定方式以定性为主。** 11 项中 9 项的相似性评价方法是「定性/图谱比对」或「直接序列比对」，
`numericLimit` 明确写「无通用数值限度」或「不适用」。只有 `free-thiol`（定量 QR）与
`n-c-terminal-sequence`（异质体比例 → QR）涉及数值区间计算。
**这意味着本大类的工具需求主要是能力层级 A-B-D，而非 E。** 把统计等效性检验当成本大类的重点是错配。

**事实三：`free-thiol` 的 `numericLimit` 里写明了 QR 公式** —— `QR=(μR−XσR, μR+XσR)`，
且要求「足够批次（如 90% 以上）落入」。这是本大类中唯一一个可以用纯数值计算完整演示的判定链路，
且输入只需要一列批次数值（CSV），不需要任何质谱原始文件。**这是最适合做端到端可行性演示的切入点。**

## 五、架构建议（读完代码库后的结论）

现状：Next.js 16 + React 19 + TypeScript 5，无后端、无测试框架、无运行时 Python 依赖。
`package.json` 仅 3 个生产依赖。数据全部静态，`next build` 全页面静态生成。

### 本轮采用的架构

```
生物类似药相似性分析系统/
├── src/data/method-tools.ts        ← 新增：工具信息静态数据（链接+用法+部署层级）
├── src/types/models.ts             ← 新增 MethodTool 类型
├── src/components/MethodToolPanel  ← 新增：在方法内容区渲染工具信息
├── tools-poc/                      ← 新增：独立 PoC 目录，与 Next.js 完全隔离
│   ├── .venv/                      ←   独立 Python 虚拟环境（不提交）
│   ├── requirements.txt            ←   锁定版本
│   ├── data/                       ←   示例与合成数据（标记来源）
│   ├── scripts/                    ←   实际运行的脚本
│   └── output/                     ←   运行输出（JSON + 日志）
└── docs/tool-survey/               ← 报告与证据
```

**关键决策：本轮不引入任何后端。** 工具信息是静态数据，PoC 是离线脚本，两者不连通。
网站保持全静态生成，零运维负担，可直接部署。

### 未来引入在线计算时的架构约束（本轮不实现，仅记录）

你要求最终支持大文件上传（含质谱原始文件），这条需求已经提前否决了两种方案：

- **纯 TypeScript 在 Next.js 服务端计算**：数百 MB 的 mzML/RAW 文件无法在 Node 中解析，排除；
- **Next.js API Route + Vercel**：Vercel 的请求体与执行时长限制远小于质谱文件处理需求，排除。

唯一可行路径是**独立 Python 服务（FastAPI）+ 对象存储 + 异步任务队列**，Next.js 仅做代理与轮询。
这是一套完整的后端基础设施，不应与本轮的可行性证明混在一起做。

## 六、实施步骤

每一步都必须留下可被第三方重现的证据。步骤编号即执行顺序，不得并行跳步。

### S1 — 分析点清单与能力需求矩阵 ✅（本文件第四节即产物）

- **目标**：从代码库抽取一级结构的全部分析点，标注每项的检测指标、判定方式、数据需求。
- **完成标准**：11 项全部列出并附行号；识别出共用方法与可演示切入点。

### S2 — 生成检索式

- **目标**：为本大类的三条技术主线（完整/亚基质谱、肽图 LC-MS/MS、巯基定量）生成中英文检索词与 GitHub 查询表达式。
- **操作**：组合分析对象英文名、方法缩写、数据格式（mzML/mzXML/RAW）、
  `biosimilar` / `comparability` / `quality range`、`pipeline` / `toolkit` / `library`。
- **产物**：`docs/tool-survey/01-primary-structure.md` 的「检索式」章节，附查询日期。
- **完成标准**：每条技术主线至少 6 组检索式，覆盖通用工具与领域专业工具两类。

### S3 — GitHub 初筛

- **目标**：每条技术主线收集 10～20 个候选仓库。
- **操作**：实时访问仓库页面核实：全名、URL、Star、Fork、最近提交、最近 Release、
  默认分支、主语言、许可证、是否归档、Issue 活跃度。
- **产物**：候选长名单表格，每行附查询日期；抓取失败的标 `[抓取失败-未验证]`。
- **完成标准**：不得仅凭搜索摘要下结论；不得虚构任何仓库或数据。

### S4 — 相关性、维护、许可证与安全初筛

- **目标**：从长名单收敛到 3～5 个短名单。
- **筛除依据**（必须逐条写明理由）：领域不匹配、长期停更、已归档、无许可证、
  依赖商业软件、仅为预处理工具而非分析工具、论文一次性脚本且有活跃替代品。
- **产物**：短名单 + 淘汰理由表。

### S5 — 精读短名单

- **目标**：确认真实能力，而非 README 宣称的能力。
- **操作**：逐个打开 README、docs、examples、tests、Releases 与关键源码；
  重点确认输入输出格式、是否自带示例数据、是否有测试、安装方式、是否依赖商业组件。
- **产物**：每个短名单工具的能力层级 A～H 判定，附具体文件或章节链接作为直接证据。

### S6 — 建立隔离运行环境

- **目标**：在 `tools-poc/` 下建立独立 Python 虚拟环境。
- **操作**：`python -m venv tools-poc/.venv`；记录 OS、Python 版本、pip 版本。
- **安全检查**：安装前先审查目标包的 `setup.py` / `pyproject.toml` / postinstall 有无可疑行为；
  来源不明的安装脚本必须先出示代码请求单独授权。
- **产物**：环境信息记录 + `requirements.txt`（锁定版本）。
- **完成标准**：不做全局安装，不修改系统 PATH，不触碰 `package.json`。

### S7 — 实际安装（推进到 L1）

- **目标**：短名单中的首选工具安装成功并打印版本号。
- **记录项**：安装命令、耗时、下载体积、退出码、完整错误信息（若失败）。
- **产物**：`docs/tool-survey/evidence/` 下的安装日志。
- **完成标准**：版本号可打印即 L1；失败也必须如实记录，不得只报成功案例。

### S8 — 官方示例数据跑通（推进到 L2）

- **目标**：用工具自带或官方发布的示例数据跑出与文档一致的输出。
- **记录项**：运行命令、参数、输入文件来源与哈希、运行时长、输出摘要、退出码。
- **产物**：运行日志 + 输出文件。
- **完成标准**：输出与官方文档描述一致才算 L2；
  仅仅「命令没报错」不算，必须有可对照的预期输出。

### S9 — 端到端最小可行性链路（推进到 L3/L4）

- **目标**：证明「从数据到判定」这条链路技术上走得通。
- **切入点**：依据第四节事实三，选择 `free-thiol` 的 quality range 判定链路，
  因为它输入只需批次数值 CSV、判定规则在 `numericLimit` 中已明确写出、
  且不依赖任何质谱原始文件。
- **链路**：合成批次数据 → 计算 μR、σR → 计算 QR=(μR−X·σR, μR+X·σR) →
  判定候选药批次落入比例 → 与 90% 阈值比较 → 输出结构化结果。
- **强制标记**：所有输入数据必须标记 `dataSource: "synthetic-demo"`，
  输出中必须携带该标记，任何展示都不得暗示这是真实测量结果。
- **产物**：可重复运行的脚本 + 输入数据 + 输出 JSON + 运行日志。
- **完成标准**：第三方按记录的命令能得到完全相同的输出。

### S10 — 输出结构化并与 models.ts 对齐（评估 L5 可行性）

- **目标**：证明 PoC 的输出能被前端消费。
- **操作**：将 S9 的输出转为 JSON，逐字段说明如何映射到 `CharacterizationItem`

- **注意**：本轮**只证明可映射，不实际接入**。达到 L5 的判定需要 JSON 真的被组件渲染，

### S14 — 实机演示必须嵌入检测方法模块（后续大类强制）

用户需求（2026-08-14）：「能实机演示非常重要；至少有一个部分能实机演示；嵌入到检测方法模块。」

**嵌入位置**：检测方法区块内、方法标签下方，即原来 `MethodContentPlaceholder`（「检测内容待嵌入」虚线框）所在位置。不得只放在页面底部的相似性分析预留区，也不得只放在工具调研卡片里。

**每个已调研且存在可运行链路的大类，至少满足：**

1. 对应方法的标签上有「实机演示」标记；
2. 选中该方法后，虚线占位被演示面板替换；
3. 用户点击「运行演示」后，计算在当前页面当场执行，改输入再算则数字改变（禁止预录动画、禁止写死一张结果图冒充运行）；
4. 默认数据必须可溯源（公开数据库或已标记的合成数据），合成数据必须在界面上明示；
5. 演示产出与框架该项目的检测指标或判定公式对应；
6. 方法学正文（原理、前处理、仪器参数）仍可待嵌入，但不得因此省略演示。

**本轮实现（一级结构，已完成）：** 浏览器端 TypeScript，不引入 Python 后端、不上传文件。覆盖完整分子质量、肽图覆盖率、游离巯基 QR。校验命令 `npm run verify:demo`。

**明确不是：** 把 UniDec/pyOpenMS 接到网站上；处理厂商 RAW；给出监管结论。

### S15 — 演示下方必须有可展开的溯源说明（后续大类强制）

用户需求（2026-08-14）：「下方有一个可点击展开的说明，数据来源、计算原理之类的。要让人相信这是真实可演示的，而不是虚构的。」

**每个实机演示面板下方必须有 `<details>` 展开区，且至少包含：**

| 小节 | 必须回答的问题 |
|---|---|
| 这是什么 | 点按钮后计算在哪里执行？改输入会不会变？ |
| 这不是什么 | 是否实测数据、是否原工具本体、是否相似性结论 |
| 数据来源 | 公开数据库 accession / 下载日期 / 哈希；或合成数据的生成脚本与种子 |
| 计算原理 | 公式或算法步骤，能对照框架 `numericLimit` / 检测指标 |
| 独立校验 | 预言机数值（如 pyOpenMS 对照、PoC JSON）与校验命令 |
| 证据文件 | 仓库内可打开的源码与日志路径 |
| 外部链接 | 可核验的 UniProt / 仓库 / 文档 URL（若适用） |

没有上述展开区的演示不得合并进检测方法模块。后续大类新增演示时，先写 `src/data/live-demo-provenance.ts` 对应条目，再挂组件。

### S16 — 方法学正文的原理必须嵌入检测方法模块（后续大类强制）

用户需求（2026-08-14）：「补充方法学正文的原理部分。」

**为什么先做原理**：S14–S15 解决了「演示是真的」，但未解决「这个方法在测什么、凭什么与相似性评价挂钩」。原理是方法学正文中唯一不依赖具体品种、不依赖厂商仪器即可写实的字段，因此优先嵌入；样品制备与仪器参数涉及品种特异的设定值，写了就会变成没有出处的伪 SOP，本轮不写。

**数据落点**：`src/data/method-content.ts`，按 `DetectionMethod.id` 索引的 sidecar。**不得**改 `characterization-items.ts`（Excel 生成文件），`contentPlaceholder: true` 保留不动。

**每条方法的原理至少回答：**

| 要点 | 必须说明 |
|---|---|
| 测什么 | 物理/化学量与它对应的分子属性 |
| 怎么测 | 分离、反应、检测的原理链条，不写具体设定值 |
| 读什么 | 输出的检测指标，与框架 `detectionIndicators` 对应 |
| 怎么判 | 定性图谱比对还是定量质量范围；与框架 `judgingPrinciple` / `numericLimit` 一致 |
| 方法边界 | 盲区与不能单独下结论之处（如 MS1 不能替代 MS/MS 序列确认） |
| 适用性 | 抗体专属项须写明非抗体产品不适用 |

**红线**：原理不得改写或软化框架已写明的判定口径；不得出现「相差 X Da 即相似」这类框架明确否定的数值线；quality range 一律写作 μR±X·σR，不得与置信区间、容许区间混用。

**渲染顺序**（`MethodSelector`）：方法学正文 → 实机演示 → 工具与部署面板。已嵌入原理的方法不再显示「检测内容待嵌入」整块虚线占位，改为在正文面板底部逐项列出仍待嵌入的字段，使「缺失」与「不适用」不会被混淆。

**完成条件**：一个大类只要有任一方法写了原理，该大类**全部**方法都必须有原理，由 `npm run verify:method-content` 机械强制（同时校验 id 链接有效、无过短的占位式正文）。

**本轮实现（一级结构，已完成）：** 33/33 条方法全部有中英原理。

**明确不是：** 可执行 SOP；经方法学验证的文本；可据以判定生物类似性的依据。

## 七、风险与预案

| 风险 | 触发条件 | 预案 |
|---|---|---|
| 质谱工具安装失败 | Windows 缺编译工具链、无预编译 wheel | 记录报错原文，改用纯 Python 实现的轻量替代，或降级到 L0/L1 并如实说明 |

| 许可证不兼容 | 工具为 AGPL 且计划对外发布 | 仅以独立进程/CLI 方式调用，禁止源码级集成，在报告中高亮 |
| 工具输出无法映射 | 输出维度与框架检测指标对不上 | 如实记录为缺口，列入「需自研模块」 |
